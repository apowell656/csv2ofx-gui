# Contributing to OpenStatement (csv2ofx-gui)

Thank you for your interest in this project! Whether you're reporting a bug,
suggesting an idea, improving the documentation or sending code, I appreciate
you taking the time.

This project is independently maintained in my spare time. I read everything
that comes in, but it may take a few days, or occasionally longer, before I can
respond. Thanks for your patience.

## Reporting bugs

1. **Search [existing issues][issues] first.** Someone may already have reported
   the problem. If so, add any new details there instead of opening a duplicate.
2. **[Open a new issue][new-issue]** and choose the bug report template.
3. **Describe how to reproduce the problem.** Step-by-step instructions are the
   most useful thing you can provide. A small made-up example is ideal.
4. **Include your environment:** the application version, your operating system
   and version, and any relevant software versions or settings.
5. **Attach logs or screenshots** if you have them.

**Please remove sensitive information** before posting anything, including
account numbers, financial details, passwords, API keys and personal data.
Issues are public, so please don't share real financial records. A fictional
example that shows the same problem works just as well.

## Suggesting features

Ideas and improvements are always welcome. When you
[open a feature request][new-issue], the most helpful thing is to explain the
problem you're trying to solve, not just the solution you have in mind.
Understanding the problem lets me find the approach that works best for
everyone.

I review every suggestion, but not every one will be scheduled. Some won't fit
the project's direction, and others may wait until there's time to do them well.

## Contributing code

Code contributions are welcome! A few things make them much easier to review:

- **Open an issue first for major features or architectural changes**, so we
  can agree on the approach before you invest a lot of time. Small fixes can go
  straight to a pull request.
- **Keep changes focused.** One fix or feature per pull request.
- **Follow the existing coding conventions** and the style of the surrounding code.
- **Add or update tests** where appropriate.
- **Update the documentation** when behavior changes.
- **Explain your reasoning.** Tell me what the change does and why.

## Pull requests

When you [open a pull request][pull-requests], please include:

- **A description of the changes** and the reasoning behind them.
- **The related issue**, if there is one (for example, "Fixes #123").
- **The testing you performed**, such as automated tests run or manual checks.

Don't worry about getting everything perfect. I'm happy to help with the rest
during review.

## Development priorities

I use issues and milestones to organize development, but priorities change as
the project evolves. An open issue, or one assigned to a milestone, isn't a
guarantee that it will land in a particular release.

## Documentation

Documentation improvements are some of the most valuable contributions. Fixing
a typo, clarifying a confusing explanation or adding an example all help other
people use the project. Small documentation fixes can go straight to a pull
request.

## Thank you

Thanks again for helping. Every bug report, idea and pull request helps keep
this software useful, reliable and maintainable.
